# 1. 一句话结论

| 问题 | 答案 |
|------|------|
| 传输层变了吗？ | **没变**。0xA5 帧头 + CRC8 + CRC16，2019 到今天一致 |
| 字段变了吗？ | **变了**。`0x0201` 加了 `chassis_power_limit`，`0x0202` 从 14 字节变 16 字节 |
| 老工程还能用吗？ | 接收框架能用；**协议结构体必须更新**，否则功率上限取不到 |
| 功率数据受影响吗？ | **不受影响**。`0x0202` 前 10 字节偏移从没变过 |
| 有 2027 版吗？ | **没有**，历年都是赛前 2~3 个月才发布 |

# 3. 帧格式

## 3.1 整体结构

```
+------------+--------+--------+----------+
| frame_header| cmd_id |  data  | frame_tail|
|   5 字节   | 2 字节 | n 字节 |  2 字节  |
+------------+--------+--------+----------+
```

## 3.2 帧头（5 字节）

| 偏移 | 大小 | 字段 | 说明 |
|------|------|------|------|
| 0 | 1 | SOF | 固定 `0xA5` |
| 1 | 2 | data_length | **data 的长度**（小端） |
| 3 | 1 | seq | 包序号，0~255 循环 |
| 4 | 1 | CRC8 | 帧头校验，范围 `[0..3]`，初值 `0xFF` |

## 3.3 ⚠️ 最容易搞错的点：data_length 到底算什么

官方表 1-3 原文：

> **data_length：数据帧中 data 的长度**

**只算 data，不含 cmd_id 和 CRC16。**

所以：

```
整帧长度 = 5(帧头) + 2(cmd_id) + data_length + 2(CRC16) = 9 + data_length
```

代码里的判据就是 `index >= 9 + data_len`（`REF_HEADER_CRC_CMDID_LEN` = 9）。

> 网上有些说法认为 `data_length` 含 cmd_id 和 CRC16（即 n+4），**那是错的**，
> 按那个造帧会被长度检查或 CRC 拒掉。

## 3.4 串口参数

| 项 | 值 |
|----|-----|
| 波特率 | 115200 |
| 数据位 | 8 |
| 停止位 | 1 |
| 校验 | 无 |
| 流控 | 无 |
| 电平 | 3.3V TTL |
| 延迟 | 正常约 130ms；网络差约 200ms |
| 丢包 | 正常 <1%；网络差约 3% |

## 3.5 两种链路

| 链路 | 走哪 | 收发口 |
|------|------|--------|
| **常规链路** | 裁判系统服务器 + 主控模块 | 电源管理模块的 **User 串口** |
| **图传链路** | 选手端 + 图传模块 | 图传模块（发送端）的串口 |

我们目前接的是**常规链路**（主控板 USART6）。

# 5. 底盘最关心的三条数据

## 5.1 `0x0201` 机器人状态（13 字节）★ 功率上限在这里

```c
typedef __packed struct
{
    uint8_t  robot_id;                        // 0  本机器人 ID
    uint8_t  robot_level;                     // 1  机器人等级
    uint16_t current_HP;                      // 2  当前血量
    uint16_t maximum_HP;                      // 4  血量上限
    uint16_t shooter_barrel_cooling_value;    // 6  枪口热量每秒冷却值
    uint16_t shooter_barrel_heat_limit;       // 8  枪口热量上限
    uint16_t chassis_power_limit;             // 10 ★ 底盘功率上限（W）
    uint8_t  power_management_bits;           // 12 bit0=gimbal bit1=chassis bit2=shooter
} robot_status_t;
```

| 偏移 | 大小 | 字段 | 单位 |
|------|------|------|------|
| 0 | 1 | robot_id | — |
| 1 | 1 | robot_level | — |
| 2 | 2 | current_HP | — |
| 4 | 2 | maximum_HP | — |
| 6 | 2 | shooter_barrel_cooling_value | — |
| 8 | 2 | shooter_barrel_heat_limit | — |
| **10** | **2** | **chassis_power_limit** | **W** |
| 12 | 1 | 电源管理输出位域 | — |

> ⚠️ **2019 版没有偏移 10 的这个字段**，老结构体读到的是别的东西。
> 功率控制要正确限流，**必须**用这个版本。

## 5.2 `0x0202` 实时功率 + 热量（16 字节）★ 功率控制的输入

```c
typedef __packed struct
{
    uint16_t chassis_voltage;      // 0  电压 mV
    uint16_t chassis_current;      // 2  电流 mA
    float    chassis_power;        // 4  功率 W
    uint16_t buffer_energy;        // 8  缓冲能量 J
    uint16_t shooter_17mm_1_heat;  // 10
    uint16_t shooter_17mm_2_heat;  // 12
    uint16_t shooter_42mm_heat;    // 14
} power_heat_data_t;
```

| 偏移 | 大小 | 字段 | 单位 |
|------|------|------|------|
| 0 | 2 | chassis_voltage | mV |
| 2 | 2 | chassis_current | mA |
| 4 | 4 | **chassis_power**（float） | **W** |
| 8 | 2 | **buffer_energy** | **J** |
| 10 | 2 | 17mm 第 1 管热量 | — |
| 12 | 2 | 17mm 第 2 管热量 | — |
| 14 | 2 | 42mm 热量 | — |

> ✅ **前 10 字节从 2019 到今天没变过**，所以老结构体拿功率和 buffer 也是对的，
> 只是后面热量字段会错（2019 只有 2 个热量字段，共 14 字节）。

## 5.3 `0x0206` 伤害状态（1 字节）

| bit | 含义 |
|-----|------|
| 0-3 | 装甲板 ID / 测速模块 ID（非装甲原因时为 0） |
| 4-7 | 扣血原因：0 弹丸攻击 / 1 模块离线 / 2 初速超限 / 3 枪口热量超限 / **4 底盘功率超限** / 5 装甲受撞击 |

> **bit4-7 == 4 说明底盘功率超限被扣血** —— 功率控制做错了会在这里看到，
> 调试时可以盯这个值。

# 6. 交互数据 0x0301 与 UI 绘制

## 6.1 数据段结构

| 偏移 | 大小 | 字段 | 说明 |
|------|------|------|------|
| 0 | 2 | data_cmd_id | 子内容 ID |
| 2 | 2 | sender_id | 发送者 ID（必须与自身 ID 匹配） |
| 4 | 2 | receiver_id | 接收者 ID |
| 6 | ≤112 | user_data | 内容数据段 |

- 整包不超过 **127 字节**
- 127 − 9（帧头+cmd+CRC16）− 6（数据段头）= **112 字节上限**
- **上行频率上限 30Hz**

## 6.2 子内容 ID

| ID | 长度 | 功能 |
|----|------|------|
| 0x0100 | 2 | 删除图层 |
| **0x0101** | **15** | **绘制 1 个图形** |
| 0x0102 | 30 | 绘制 2 个图形 |
| 0x0103 | 75 | 绘制 5 个图形 |
| 0x0104 | 105 | 绘制 7 个图形 |
| 0x0110 | 45 | 绘制字符 |
| 0x0120 | 4 | 哨兵自主决策 |
| 0x0121 | 1 | 雷达自主决策 |
| 0x0200~0x02FF | ≤112 | 机器人之间自定义通信 |

## 6.3 图形结构（`0x0101`，15 字节）

```c

{
```

## 6.5 坐标系与注意点

- **(0,0) = 屏幕左下角；(1920,1080) = 右上角**
- 角度：**0° 指向 12 点钟方向，顺时针**

- 线宽:字号 建议 **1:10**
- 图层 0~9，删除时可按图层或全部删除

# 7. 发送须知

| 项 | 限制 |
|----|------|
| 0x0301 上行频率 | **≤30Hz** |
| 英雄/工程/步兵/空中/飞镖 | 每 1000ms 接收 **≤3720 字节** |
| 雷达 / 哨兵 | 每 1000ms 接收 **≤5120 字节** |

换算一下：一帧 UI（15 字节图形）整包约 **9 + 6 + 15 = 30 字节**，
30Hz 全速刷 = 900 字节/秒，远低于 3720 的上限，**安全**。

> 但别把多个 0x0301 内容 ID 同时高频刷——整个 cmd_id 的上行频率上限是 30Hz 共享的。

# 9. 没有裁判系统怎么验证

**结论：完全可以验证，不需要裁判系统。** 协议就是固定字节流，谁发都一样。

## 9.1 路径 A：PC 串口注入（推荐）

```
USB-TTL (3.3V 档) TX  →  主控板 PG9 (USART6_RX)
USB-TTL            GND →  主控板 GND
```

PC 端按下面的格式造帧，10Hz 发送：

```
A5 0B 00 01 CRC8 02 02 <16 字节数据> CRC16
   └data_len=11┘  └seq ┘      └cmd_id 0x0202┘
```

`0x0202` 的 16 字节 = 13 字节数据 + 2 字节 CRC16，所以 `data_length = 11`（13−2）。

> 更准确地说：`data_length` = 该命令表里写的"数据段长度"减去 CRC16 的 2 字节。
> 例：`0x0201` 表写 13 → 实际 `data_length = 11`；`0x0202` 表写 16 → `data_length = 14`。

⚠️ 这里容易绕，最稳的办法是**抓一帧真裁判数据**看 `data_length` 字段。

## 9.2 路径 B：纯软件单元测试

把 `referee_data_solve()` + CRC 抽出来，PC 上 gcc 编译，喂构造帧。
不需要任何硬件，适合先验证解析和字段偏移。

## 9.3 路径 C：旧裁判系统

能用，但旧版 `0x0201` 没有 `chassis_power_limit`，**用新结构体解析会错位**。
只能验证物理链路和状态机，不能验证新字段。

## 9.4 验证清单

| # | 条件 | 通过标准 |
|---|------|---------|
| 1 | 注入 `0x0201` | `robot_id` / `level` / `max_HP` / `power_limit` 与构造值一致 |
| 2 | 注入 `0x0202` | `voltage=24000`、`power`、`buffer=45` 对得上 |
| 3 | 停发 1s | 离线标志置位 |
| 4 | 改 1 bit | 该帧被丢，不污染其他数据 |
| 5 | 连发 100 帧 | 计数正确，无丢帧 |

# 10. 常见坑清单

| # | 坑 | 说明 |
|---|-----|------|
| 1 | `data_length` 理解错 | **只算 data**，整帧 = 9 + data_length |
| 2 | `0x0201` 用 2019 结构体 | 功率上限读成别的值，限流失效 |
| 3 | `0x0301` 用 113 字节 | V1.6.4/V1.7/2026 都是 **112** |
| 4 | UI 坐标搞反 | (0,0) 在**左下角**，不是左上角 |
| 5 | 浮点不除 1000 | 显示值会大 1000 倍 |
| 6 | 频繁刷 UI | 整体 30Hz 上限是**所有内容 ID 共享**的 |
| 7 | 结构体没 `__packed` | 成员按 4 字节对齐，整包错位 |
| 8 | 用裁判数据做闭环 | 10Hz + 130ms 延迟，**只能做慢环**（功率环用模型） |
| 9 | 忘了队色 | 颜色 0 是"己方颜色"，红蓝自动适配 |
| 10 | 收发共用判断 | 命令是**单向**的，机器人只能发 0x0301/0x0302/0x0306 等 |
