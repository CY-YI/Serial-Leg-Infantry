# 1. 现状盘点：我们现在有什么

## 1.1 现有底盘代码的数据流

```
chassis_task（2ms 循环）
  │
  ├─ 阶段1  chassis_set_mode()      拨杆/键盘/掉线 → FOLLOW | revolve | LOCK
  ├─ 阶段2  chassis_set_control()   FOLLOW：摇杆→Ramp→vx/vy（RPM）；follow 双环→v_rot
  ├─ 阶段3  chassis_set_v()         revolve：低通+×5→vx/vy；v_rot = V_REVOLVE
  ├─ 阶段4  ChassisController()     等比缩放限幅 → 麦轮逆运动学 → 四轮目标 RPM
  │           └─ ChassisPidCtr()    ★ 四轮 PID → 电流指令（int16）
  ├─ 阶段5  CAN_cmd_chassis()       0x200 帧发送（FL, FR, BL, BR）
  └─ 阶段6  心跳（loop_count / tick_delta）
```

## 1.2 现在功率限制在哪

`ChassisPidCtr()` 末尾（当前是**占位**）：

```c
get_chassis_power_and_buffer(&power, &power_buffer);   // 空壳，返回 (0W, 50)

if (power_buffer < POWER_BUFFER_FIXED)                 // 50 < 50 → 永不成立
{
    // Σ|四输出| → Limit = buffer²×6 → 等比缩放
}
```

**结论：当前完全没有功率限制。** 因为 buffer 恒为 50，分支永远进不去。

## 1.3 我们现在有什么、没有什么

| 资源 | 状态 | 对功率控制的意义 |
|------|------|-----------------|
| 四轮转速反馈 `speed_rpm` | ✅ 有 | 模型必需，够用 |
| 电流指令（我们自己发的） | ✅ 有 | 模型输入 |
| 力矩常数/减速比 | ✅ 手册可查 | 换算系数 |
| 裁判系统（功率/缓冲） | ❌ 没有 | 只能开环用模型 |
| 超级电容 | ❌ 没有 | 无法扩展 P_max |
| 功率测量（电流传感器） | ❌ 没有 | 无法在线标定 k1/k2 |
| 电池 + 电源管理模块 | ✅ 有 | 供电没问题（远大于 80W） |

**这意味着：第一阶段只能做"纯模型"方案，没有任何反馈校正。** 这一点必须在设计上就承认。

# 2. 三种落地路径对比（怎么塞进工程）

## 路径 A：直接写在 `ChassisPidCtr` 里

```
改造 chassis.c 的 ChassisPidCtr，把功率计算塞进去
```

| 优点 | 缺点 |
|------|------|
| 改动最小，不新增文件 | `ChassisPidCtr` 会膨胀到 150+ 行 |
| 保持"老版单文件"风格 | 功率算法和底盘解算耦合，难单独测试 |
| 不用改 uvprojx | 以后接裁判/超电要反复改同一个函数 |

**适合**：只想快速做个"能超限就砍"的最小版本。

## 路径 B：新建 `chassis_power.c/h` 独立模块（推荐）

```
chassis.c  ──调用──▶  chassis_power.c
   │                     │
   └─ PID 输出 ─────────▶ │ 模型预测 + 分配 + 求解
                         │
      最终电流 ◀──────────┘
```

| 优点 | 缺点 |
|------|------|
| 职责单一，可单独仿真测试 | 新增 2 个文件，要登记进 `.uvprojx` |
| 接裁判/超电只改模块内部 | 偏离"老版单文件"风格（但你已同意功率这块可以不沿用） |
| 参数集中，方便标定 | 多一层函数调用（开销可忽略） |
| 断连降级逻辑有地方放 | — |

**适合**：要长期演进（裁判 → 超电 → RLS）。

## 路径 C：完全照搬港科大的 Manager 结构

```
class Manager { motors; k1; k2; k3; rls; powerBuff; ... }
PowerObj obj[4]; getControlledOutput(obj);
```

| 优点 | 缺点 |
|------|------|
| 功能最全（RLS、能量环、错误处理） | C++ 模板/命名空间，我们是 C 工程 |
| 经过实战验证 | 依赖裁判 + 超电 + 电机抽象层，我们没有 |
| — | 移植成本高，容易"看不懂也改不动" |

**适合**：等 P3/P4 阶段、且愿意大改架构时。

## 结论

> **走路径 B**：新建 `chassis_power.c/h`，**用 C 写**，结构参考港科大但裁掉我们没有的部分（RLS、超电、C++ 抽象）。

# 3. 推荐框架：独立模块 + 快慢双环

## 3.1 整体结构

```
┌─────────────────────────────────────────────┐
│ chassis_task（2ms）                          │
│                                             │
│  ① 解算 + PID  →  得到四个 pid_output        │
│         │                                   │
│         ▼                                   │
│  ② chassis_power_apply()   ← 快环（500Hz）   │
│         │   · 模型预测总功率                  │
│         │   · 超限则分配 + 二次求解           │
│         ▼                                   │
│  ③ 最终电流 → CAN_cmd_chassis()              │
└─────────────────────────────────────────────┘
                    ▲
                    │ P_max / k1 k2 k3 / buffer
                    │
┌─────────────────────────────────────────────┐
│ 慢环（10Hz，裁判数据到达时）                   │
│  chassis_power_update(measured, buffer, ok) │
│    · 更新实测功率（将来给 RLS 用）             │
│    · 能量环 → 新的 P_max                     │
└─────────────────────────────────────────────┘
```

## 3.2 两个环的职责

| | 快环 `apply()` | 慢环 `update()` |
|---|---|---|
| 频率 | 2ms（每个底盘周期） | 10Hz（裁判帧到达） |
| 输入 | 电流指令 + 转速反馈 | 实测功率 + 缓冲能量 |
| 输出 | 最终四路电流 | 功率上限 P_max |
| 缺数据时 | 永远能跑（模型自给自足） | 跳过，沿用旧值 |
| 关键性 | **必需** | 可选（没有裁判就退化） |

**核心设计原则：快环不依赖任何外部数据源。** 这样即使裁判断连、超电没装，功率限制依然生效。

## 3.3 为什么慢环不放在 `chassis_task` 里

裁判数据通过串口中断/DMA 到达，频率与底盘任务不同步。

两种做法：
- **做法1**：在 `chassis_task` 里检查"有没有新数据"，有就更新（简单，推荐）
- **做法2**：单独建一个裁判解析任务（更规范，但多一个任务）

**推荐做法1**：底盘 2ms 跑得比裁判 100ms 快得多，检查标志位就够了，不用加任务。

# 4. 接口与数据结构设计

## 4.1 数据结构

```c
/* 每个轮子交给功率模块的信息 */
typedef struct
{
    float pid_output;    /* PID 算出的电流指令（可正负）        */
    float max_output;    /* PID 本身的输出限幅（不能超过）      */
    float cur_av;        /* 实际角速度 rad/s（由 speed_rpm 换算）*/
    float set_av;        /* 目标角速度 rad/s（由目标 RPM 换算）  */
} chassis_power_obj_t;

/* 对外暴露的状态（VOFA 观测用） */
typedef struct
{
    float max_power;         /* 当前生效的功率上限 W          */
    float sum_power_cmd;     /* 限幅前预测总功率 W            */
    float sum_power_out;     /* 限幅后预测总功率 W            */
    float measured_power;    /* 裁判实测功率 W（无裁判为 0）   */
    float buffer;            /* 缓冲能量 J（无裁判为 0）       */
    uint8_t clamped;         /* 本周期是否触发了限幅 0/1       */
    uint8_t source;          /* P_max 来源：0=默认 1=裁判 2=超电 */
    uint8_t referee_ok;      /* 裁判数据是否有效              */
} chassis_power_status_t;
```

## 4.2 接口

```c
/* 初始化：传入标定好的模型参数（只在 pid_all_init 附近调用一次） */
void chassis_power_init(float k1, float k2, float k3,
                        float torque_const, float output_to_current);

/* 外部改写功率上限：无裁判时给常量，有裁判时给实测值，有超电时给扩展值 */
void chassis_power_set_max(float max_power);

/* 慢环：裁判数据到达时调用 */
void chassis_power_update(float measured_power, float buffer, uint8_t valid);

/* 快环：每个底盘周期调用，输入 PID 结果，输出最终电流 */
void chassis_power_apply(const chassis_power_obj_t obj[4], int16_t out[4]);

/* 观测 */
const chassis_power_status_t *chassis_power_get_status(void);
```

## 4.3 为什么是这个形状

| 设计 | 理由 |
|------|------|
| `apply()` 用输入/输出参数，不用全局 | 好测试，单元测试里可以造假数据 |
| `set_max()` 独立 | 这是"策略"和"算法"的分界点，将来超电只改调用方 |
| `update()` 可为空 | 没裁判时一次都不调，模块照样工作 |
| 状态结构体只读 | 防止上层误改内部状态 |

# 5. 与现有代码的衔接点

## 5.1 改动清单

| 文件 | 改什么 | 影响 |
|------|--------|------|
| `application/chassis_power.c/h` | **新增** | 无 |
| `application/chassis.c` | `ChassisPidCtr` 里把 PID 结果交给 `chassis_power_apply` | 只改函数体内部 |
| `application/chassis.c` | 删掉老的空壳功率限制（`get_chassis_power_and_buffer`） | 删除死代码 |
| `TEST/pid_init.c` | 调用一次 `chassis_power_init(...)` | 加一行 |
| `MDK-ARM/Serial Leg Infantry.uvprojx` | 登记两个新文件 | 必须，否则不参与编译 |
| `application/chassis.h` | 加功率相关的 VOFA extern | 加几行 |

## 5.2 `ChassisPidCtr` 改造前后的对比

**改造前**（当前）：

```c
void ChassisPidCtr(...)
{
    if (LOCK) { PID_clear ×4; 输出清零; return; }

    out1 = PID_calc(&pid_fl, fdb_fl, tgt_fl);
    out2 = PID_calc(&pid_fr, fdb_fr, tgt_fr);
    out3 = PID_calc(&pid_bl, fdb_bl, tgt_bl);
    out4 = PID_calc(&pid_br, fdb_br, tgt_br);

    /* 功率限制占位：永不触发 */
}
```

**改造后**：

```c
void ChassisPidCtr(...)
{
    if (LOCK) { PID_clear ×4; 输出清零; return; }

    /* 1) 先拿到原 PID 输出 */
    raw[0] = PID_calc(...);  raw[1] = ...;  raw[2] = ...;  raw[3] = ...;

    /* 2) 填功率对象 */
    for (i = 0; i < 4; i++)
    {
        obj[i].pid_output = raw[i];
        obj[i].max_output = PID_MAX_OUT;
        obj[i].cur_av     = rpm_to_rad(raw_fdb[i]);
        obj[i].set_av     = rpm_to_rad(raw_tgt[i]);
    }

    /* 3) 功率限幅（内部决定是原样输出还是重算） */
    chassis_power_apply(obj, final);

    /* 4) 写入结构体（注意这里是 int16 输出，不是原先的 int16 PID 结果） */
    chassisparam.LefUpFinalOutValue = final[0];
    ...
}
```

**注意点**：

1. `LOCK` 分支必须**提前返回**，不要让功率模块去处理 LOCK（否则它会把 0 当成"要限幅"）
2. `chassis_power_apply` 内部要保证输出不超过 `max_output`
3. 四路槽位顺序必须与 `CAN_cmd_chassis(FL, FR, BL, BR)` 一致

## 5.3 关于 `revolve` / `FOLLOW` 模式

功率限制**与模式无关**——不管哪种模式，最终都是四路电流，都要过功率模块。

唯一区别：`LOCK` 时不调用（直接发 0）。

## 5.4 初始化时机

```c
void pid_all_init(void)   /* TEST/pid_init.c */
{
    ...
    chassis_power_init(K1_DEFAULT, K2_DEFAULT, K3_DEFAULT,
                       KT_M3508, OUTPUT_TO_CURRENT);
    chassis_power_set_max(POWER_LIMIT_DEFAULT);   /* 无裁判时的保守值 */
}
```

放在 `pid_all_init` 里是因为它已经在 `main` 初始化流程中被调用，且是"参数初始化"的天然位置。

# 6. 分阶段实施（MVU-7.x）

> 每个 MVU 都是"能独立验证、能独立回滚"的最小单元。

## MVU-7.1　观测版（只算不控）

**目标**：验证模型算得准不准，**不做任何限幅**。

| 项 | 内容 |
|----|------|
| 改动 | 新增 `chassis_power.c/h`，只实现"预测总功率"并输出到 VOFA |
| 验证 | 台架四轮悬空，逐步加大电流，看 `chassis_power_estimate` 是否随电流平方增长 |
| 验收 | 堵转时预测值明显 > 0（说明 τ² 项生效） |
| 回滚 | 删两个文件 + uvprojx 登记项 |

**为什么先做这个**：模型不准，后面所有限幅都是错的。**先测量，再控制。**

## MVU-7.2　等比限幅（最小可用）

**目标**：超限时四路等比缩小，先解决"会超功率"的问题。

| 项 | 内容 |
|----|------|
| 改动 | `apply()` 里加：`if (P_cmd > P_max) scale = P_max / P_cmd; 四路 × scale` |
| 验证 | 台架给大电流，看 `clamped` 标志和缩放系数 |
| 验收 | 预测功率不再超过 P_max |
| 已知缺陷 | 会走不直（下一步解决） |

## MVU-7.3　功率分配（误差加权）

**目标**：解决"限幅后走不直"。

| 项 | 内容 |
|----|------|
| 改动 | 把"四路同比缩放"换成"按误差/功率混合权重分配" |
| 验证 | 台架：四轮悬空，人为给不同目标，看分配是否偏向误差大的轮 |
| 验收 | 直线行驶时限幅前后方向偏差 < 明显可感 |
| 参数 | `E_lower`（≈15）、`E_upper`（≈20） |

## MVU-7.4　二次方程求解（从"缩电流"升级到"按功率反解"）

**目标**：不再是简单缩放，而是"每个轮子按分到的功率，解出最大力矩"。

| 项 | 内容 |
|----|------|
| 改动 | `apply()` 里加二次方程求解（含判别式三种情况） |
| 验证 | 同一目标下，7.4 的输出应 ≤ 7.3 的输出，但更"精准" |
| 验收 | 高速+大电流工况下不超功率；低速时不被过度限制 |
| 回滚 | 保留 7.3 的实现做 A/B 对比 |

## MVU-7.5　裁判接入 + 能量环

**目标**：有实测数据后，让 P_max 动态化。

| 项 | 内容 |
|----|------|
| 前置 | 裁判系统串口接通，能解析 0x0201 / 0x0202 |
| 改动 | `chassis_power_update()` 实现 + 能量环 PD + 断连降级 |
| 验证 | 跑圈看 buffer 是否稳定在 40~50J |
| 验收 | 整场不扣血；buffer 不持续下降 |

## MVU-7.6　RLS 自标定（可选）

**目标**：参数自动收敛，减少标定工作量。

| 前置 | 有稳定实测功率 |
| 改动 | 引入 2 阶 RLS（港科大 `Utils/RLS.hpp` 的 C 移植） |
| 验收 | k1/k2 在几分钟内收敛且不再漂移 |

## MVU-7.7　超电接入（硬件到位后）

| 改动 | `set_max()` 改为 `裁判上限 + 超电可用功率`；能量环闭环 SOC |
|------|------|

# 7. 裁判系统接入方案

> 即使现在没有裁判，也要先把接口留好，否则 7.5 要返工。

## 7.1 需要解析的报文

| 报文 | 关键字段 |
|------|---------|
| `0x0201` 机器人状态 | `chassis_power_limit`（W）、`robot_level`、`current_hp`、`max_hp` |
| `0x0202` 实时功率 | `chassis_volt`(mV)、`chassis_current`(mA)、`chassis_power`(W)、`chassis_power_buffer`(J) |

> 字段顺序与单位**以当年官方协议手册为准**，不同赛季可能微调。

## 7.2 数据流

```
裁判串口（DMA 空闲中断）
   ↓
解析帧头 + 校验
   ↓
按 CMD_ID 分发
   ├─ 0x0201 → 更新 power_limit / level / hp
   └─ 0x0202 → 更新 voltage / current / power / buffer，置"新数据"标志
   ↓
chassis_task 每 2ms 检查标志
   ↓
chassis_power_update(...)   ← 慢环
```

## 7.3 断连检测

```c
if (HAL_GetTick() - referee_last_tick > 500)   /* 500ms 无新帧 */
{
    referee_ok = 0;
    /* 降级：沿用最后一次有效的 power_limit；若从未收到过，用默认值 */
}
```

**降级策略**：

| 情况 | P_max 取值 |
|------|-----------|
| 从未收到裁判数据 | `POWER_LIMIT_DEFAULT`（建议 60W，保守） |
| 曾收到，后断连 | 最后一次有效 `chassis_power_limit` |
| 恢复 | 立即切回实时值 |

## 7.4 数据滤波

裁判 10Hz 数据会抖，`buffer` 尤其明显。

```c
buffer_filtered = 0.7 * buffer_filtered + 0.3 * buffer_raw;
```

**只对 buffer 滤波，别对 power 滤波**——power 用于诊断对比，滤波会掩盖真实值。

# 8. 三种方案横向对比：老版 / 港科大 / 我们的裁剪版

## 8.1 逐维度对比

| 维度 | 老版（橙子） | 港科大 RM2024 | **我们的裁剪版** |
|------|-------------|--------------|-----------------|
| 功率模型 | ❌ 无 | ✅ τ·ω + k1\|ω\| + k2τ² + k3 | ✅ 相同 |
| 参数获取 | ❌ 无 | ✅ RLS 在线自标定 | ⚠️ 先借默认值，P4 再接 RLS |
| 功率预测 | ❌ 无 | ✅ 每周期预测 | ✅ 相同 |
| 限幅方式 | 等比缩放 | 误差加权分配 + 二次求解 | ✅ 分阶段：先等比，后升级 |
| 能量环 | ❌ 无 | ✅ PD 闭环 | ⚠️ P3 才做（需裁判） |
| 超电支持 | ❌ 无 | ✅ | ❌ 本期不做 |
| 断连处理 | ❌ 无 | ✅ 四种场景 | ✅ 只做"裁判断连"一种 |
| 语言/架构 | C 单文件 | C++ 模板 + 命名空间 | **C 模块**（与工程一致） |
| 依赖 | 无 | 裁判 + 超电 + 电机抽象层 | **只依赖电机反馈** |
| 代码量（估） | ~20 行 | ~900 行 | **~250 行** |
| 上手难度 | 低 | 高 | 中 |

## 8.2 为什么砍掉这些

| 砍掉的功能 | 理由 |
|-----------|------|
| RLS 自标定 | 需要真实功率反馈，我们现在没有；先用默认值 |
| 超电调度 | 硬件还没装 |
| C++ 抽象层 | 我们是纯 C 工程，引入 C++ 不划算 |
| 舵轮/轮腿分支 | 我们是麦轮，用不上 |
| 四种断连场景 | 只做"裁判断连"，其余没有数据源也无意义 |

## 8.3 为什么保留这些

| 保留 | 理由 |
|------|------|
| 二次方程求解 | 这是"不破坏运动学"的关键，等比缩放做不到 |
| 误差加权分配 | 解决"走不直"的核心 |
| 慢环/快环分离 | 结构上必须，否则 10Hz 数据拖累 500Hz 环 |
| `set_max()` 接口 | 为裁判/超电预留，避免返工 |

# 9. 性能与实时性评估

## 9.1 计算量

每个 2ms 周期需要做（四轮）：

```
4 次 ρ（模型预测）：约 4 × 6 次乘加
4 次判别式 + 开方：4 次 sqrtf
若干次除法
```

| 项目 | 估算 |
|------|------|
| 浮点运算次数 | ~100 次（含 4 次 sqrt） |
| STM32F407 @168MHz + FPU | 单精度 sqrt ≈ 14 周期 |
| 预计耗时 | **< 20µs** |
| 占 2ms 周期比例 | **< 1%** |

**结论：完全没压力。** 不用担心性能。

## 9.2 内存

- 状态结构体：~40 字节
- 四个 PowerObj：~64 字节
- 总计 < 200 字节

**对 128KB RAM 无影响。**

## 9.3 栈

`chassis_power_apply` 内部只需要几个 float 局部变量，**栈增量 < 100 字节**。
现有 chassis 任务栈 512 字（2KB），够用。

# 10. 风险清单与防护

| # | 风险 | 后果 | 防护 |
|---|------|------|------|
| 1 | `k1/k2/k3` 单位搞错（ω 用 RPM 还是 rad/s） | 模型全错，限幅失效或过度 | 代码里统一用 rad/s，注释写死 |
| 2 | `k0`（输出→力矩）算错 | 预测功率差一个数量级 | 用额定点反算校验：`τ_rated = Kt × I_rated` |
| 3 | 除零：`sumError = 0` | NaN → 输出乱跳 | 加 `< 1e-4` 判据回退 |
| 4 | 除零：`k2 = 0` | 二次方程退化 | `k2` 必须 > 0，初始化时断言 |
| 5 | 判别式为负后开方 | NaN | 先判断 `Δ > 0` 再 `sqrtf` |
| 6 | 缩放后 `int16` 溢出 | 电流异常 | 输出前 `clamp(-32768, 32767)`，并受 `max_output` 限制 |
| 7 | 裁判 `power` 单位（W 还是 0.1W） | P_max 差 10 倍 | 上电后与 `V×I` 交叉验证一次 |
| 8 | 裁判断连未检测 | 用过期 P_max | 500ms 超时降级 |
| 9 | LOCK 时仍调用限幅 | 输出被改写 | `ChassisPidCtr` 提前 return |
| 10 | 新增文件未登记 uvprojx | 链接报未定义符号 | 改完必须编译验证 |
| 11 | 文件写入丢了 BOM | Keil 中文注释乱码 | 每次改完跑 `tools/ensure_bom.py` |
| 12 | 台架电源限流干扰标定 | k1/k2 拟合错误 | 标定必须用电池（见 CH-06） |

# 12. VOFA 观测变量设计

| 变量 | 类型 | 含义 | 正常范围 |

## 13.3 单位约定（最容易错的地方）

| 量 | 单位 | 说明 |
|----|------|------|
| 电机转速反馈 `speed_rpm` | RPM（转子） | bsp_can 解析出来就是这个 |
| 模型里的 ω | **rad/s** | 必须换算：`ω = RPM × 2π/60` |
| 电流指令 | 整数（-16384~16384） | 与 `PID_calc` 输出同量纲 |
| 力矩 τ | N·m | 转子侧 |
| 功率 | W | — |
| 能量 | J | — |

> **换算错误是这套系统最常见的 bug 来源。** 建议所有函数入参都用"已经换算好的 rad/s"，换算只在一个地方做。
